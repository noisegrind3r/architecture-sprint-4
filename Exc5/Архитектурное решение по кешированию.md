Архитектурное решение по кешированию

1. Мотивация
  в первую очередь, внедрение кэширования поможет решить проблему с долгой загрузкой стартовой страницы системы MES, где отображается список заказов. В дальнейшем, данный подход можно использовать для других данных, которые не часто меняются и имеют проблему с производительностью при отображении, например: история заказов или история расчета моделей.
  также, внедрение кэширования имеет следующие преимущества:
  - ускорение работы системы
  - снижение нагрузки на сервисы БД и API, также это поможет снизить затраты на вычислительные ресурсы облачных серверов, так как позволит использовать менее мощное оборудование
  - кэширование может повысить отказоустойчивость системы - в случае падения сервиса БД, запросы некоторое время могут обрабатываться сервисом кэша, что позволит уменьшить время downtime серверов
  - кэширование позволит упростить масштабирование системы при росте пользователей ценой невысоких затрат

2. Предлагаемое решение
  для внедрения кэширования предлагается использование серверного кэширования, так как статус заказов важная информация и пользователи должны видеть актуальные данные, а в случае клиентского кэширования приложение имеет ограниченный контроль над данными, что может привести к устареванию информации на стороне клиента, например, при проблемах сети, и показывать недостоверные данные, что вызовет неудовольствие клиентов. Также, клиентское хранилище имеет ограничение на объем, что может вызывать проблемы при использовании кэширования в будущем. 
  
  Для внедрения предлагается использование стратегии кэширования Write-Behind, так как она позволит получать всегда актуальные данные с высокой скоростью отклика. В случае, если при записи данных в БД произойдет ошибка, необходимо добавить логирование этого участка кода и оповещения членам команды для оперативного решения проблемы.
   - стратегия Cache-Aside не подходит из-за возможной несогласованности данных в кэше с БД
   - стратегия Read-Through не подходит из-за необходимости иметь одну модель данных в БД и кэше, что затрудняет внесение изменений в функционал
   - стратегия Refresh-ahead может вызывать избыточное чтение данных из БД и не дать большой выигрыш в снижении нагрузки
   - стратегия Write-Through вынуждает пользователей ждать ответа при изменении статуса заказа, что может вызывать их недовольство 

  В качестве стратегии инвалидации кэша предлагается использовать подход "Инвалидация, основанная на запросах": при изменении статуса заказа порождается событие, которое вызывает пересчет кэша для заказа. Также, для дополнительной страховки, в случае проблем с событиями, предлагается добавить стратегию "Временная инвалидация", что позволит получить актуальные данные, в случае сбоев, пусть и не сразу
   - стратегии "инвалидация на основе изменений" и "программная инвалидация" будет избыточны в данном случае, так как статус заказа меняется не слишком часто
   - стратегия "инвалидации по ключу" сложней в реализации и более чувствительна к ошибкам, но также может использоваться в качестве альтернативного решения совместно с временной инвалидацией 

  В качестве инструмента для реализации тестирования предлагается выбрать систему Redis с использованием кластеризации для повышения отказоустойчивости
