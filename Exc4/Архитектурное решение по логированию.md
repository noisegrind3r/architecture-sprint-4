Архитектурное решение по логированию

1. Список необходимых логов с уровнем INFO:
  - неверно введенный пароль: время попытки, логин
  - вызванный метод API: время вызова, имя метода, ip-адрес
  - создание заказа: время создания, состав заказа, идентификатор заказа, пользователь, тип заказа (своя система или сторонняя)
  - изменение статуса заказа: текущий статус, предыдущий статус, время изменения, идентификатор заказа, пользователь, тип заказа
  - удаление или отмена заказа: время удаления, идентификатор заказа, пользователь, тип заказа
  - расчет стоимости модели: идентификатор заказа, время старта, время окончания, идентификатор модели
  - отправка сообщения в очередь брокера сообщений: идентификатор заказа, время отправки
  - получение сообщения из очереди брокера сообщений: идентификатор заказа, время получения
  
  для сбора логов с пометкой WARNING, предлагаю отправлять данные об обработанных ошибках в сервисах API
  для сбора логов с пометкой ERROR,  предлагаю отправлять данные об необработанных ошибках в сервисах API
  для сбора логов с пометкой FATAL,  предлагаю отправлять данные о потери связи сервисов API с БД и брокером сообщений

  дополнительно, собирал бы все логи приложений API, баз данных, брокера сообщений; логи контейнеров; системные логи серверов для последующего анализа и обработки

2. Мотивация
 - улучшение диагностики и отладки: позволит быстрее устранять проблемы и узнавать о них раньше пользователей
 - мониторинг производительности: позволит определить узкие места системы и принять решение о масштабировании или исправлении проблем с производительностью
 - безопасность: позволит узнать о попытках взлома или DDOS-атаках

 в первую очередь необходимо настроить логирование для сервисов MES API и CRM API как самых проблемных и важных участках системы

3. Предлагаемое решение:
   предлагается использовать стек Prometheus для сборка и хранения логов и Grafana для их визуализации, Alert Manager Для оповещений,  собирать данные с сервисом можно с помощью Exporter. Данные технологии предлагается использовать также для мониторинга, поэтому их внедрение не потребует больших затрат времени и дополнительных вычислительных мощностей.

 [Ссылка на схему системы](https://github.com/noisegrind3r/architecture-sprint-4/blob/sprint_4/Exc4/jewerly_c4_model.drawio.png)

  политика безопасности в отношении логов включает в себя аутентификацию, авторизацию по ролям и обезличивание для чувствительных данных.

  политика хранения в отношении логов включает в себя следующее 
 - отдельный индекс под системы API
 - отдельный индекс под системы БД
 - отдельный индекс под брокер сообщений
 
  период хранения логов:
    - логи API хранить 6 месяцев, в дальнейшем архивировать и удалять совсем старые архивы по мере возникновения проблем с местом хранения
    - логи БД хранить 1 месяц
    - логи брокера сообщений хранить 1 месяц

4. Проработайте необходимые мероприятия для превращения системы сбора логов в систему анализа логов

 для выполнения данного требования предлагается использовать:
  - систему Grafana для визуализации агрегированных данных логов: например, среднее время выполнения заказа, количество зависших заказов и т.д.
  - Alert Manager для уведомлений о важных событиях: зависший заказ, большое количество запросов к API, большое количество неудачных попыток вход и т.д.
