Архитектурное решение по трейсингу

1. Части системы, которые необходимо покрыть трейсингом:
  - CRM API
  - MES API
  необходимо покрыть трейсингом только эти системы, исходя из того, что только они обмениваются данными через брокер сообщений. Все остальные проблемы можно выявить из логов или мониторинга.
  в дальнейшем, трейсинг необходимо будет подключить к Shop API, после того как база ShopDB будет разделена у сервисов Shop API и CRM API и настроен обмен данным между данными сервисами через брокер сообщений.

2. Мотивация
  в первую очередь, трейсинг необходим для того чтобы найти и решить проблему с заказами. Диагностировать место, где заказы теряются или слишком долго обрабатываются. 
  в дальнейшем, трейсинг поможет выявлять другие проблемы:
   - медленную работу системы, позволит выявить узкие места и оптимизировать работу
   - пропадающие запросы между сервисами
  данные собранные с помощью трейсинга помогут спланировать дальнейшее развитие и улучшение продукта

3. Предлагаемое решение:
  для реализации данного подхода предлагается использование системы Jaeger для сбора и хранения метрик.
  в качестве визуализации данных предлагается использование Jaeger UI.
  для непосредственного сбора данных метрик с сервисов предлагается использование OpenTelemetry SDK, потребуется доработать код сервисов в части добавления методов OpenTelemetry

 [Ссылка на схему системы](https://github.com/noisegrind3r/architecture-sprint-4/blob/sprint_4/Exc3/jewerly_c4_model.drawio.png)

4. Компромиссы:
  - внедрение трейсинга может потребовать значительных трудозатрат для интеграции с системами, особенно с MES API, так как система разработана за пределами команды
  - внедрение трейсинга может вызывать дополнительную нагрузку на систему, которая и так, возможно, сталкивается с высокой пользовательской нагрузкой, что потребует вертикального масштабирования серверных мощностей
  - конфиденциальная пользовательская информация может оказаться доступной всем членам команды и привести к нежелательным утечкам

5. Аспекты безопасности:
  - для избежания нежелательных утечек данных предлагается использование аутентификации для того, чтобы посторонние не получили доступ и авторизации по ролям пользователей, чтобы, например, новички в команде не видели определенные данные
  - также, бороться с утечками данных поможет обезличивание чувствительной информации на этапе сбора метрик (например, ФИО пользователей их числовыми идентификаторами)
